# 8-track

Workspace for enabling tracks 5–8 on the Roland MC-101 v1.82.

- **Plan and scouting report:** [`8-TRACK.md`](8-TRACK.md)
- **Patch-site inventory:** [`manifest/sites.json`](manifest/sites.json)
- **Schema notes:** [`manifest/README.md`](manifest/README.md)

## Quick start

First, download and extract the stock MC-101 v1.82 firmware archive into `vendor/mc101_sys_v182/` (see [Setup & Building the Patched Firmware](../README.md#setup--building-the-patched-firmware) in the top-level README, as well as the extracted Core 0/Core 1 payloads under `vendor/mc101_sys_v182/extracts/`).

```bash
# Build and verify both Core 0 (RPG69_C0A_up.bin) and Core 1 (RPG69_C1A_up.bin)
python3 8-track/build.py

# Verify only (checks stock manifest + any existing outputs)
python3 8-track/build.py --verify-only

# Regenerate manifest/sites.json from tools/gen_manifest.py, then build & verify
python3 8-track/build.py --regen-manifest
```

Outputs are written to `build/8-track/out/`:
- `RPG69_C0A_up.bin` — Core 0 firmware update container (`App1_Main_decrypted.8track.bin` also emitted)
- `RPG69_C1A_up.bin` — Core 1 QSPI update container

Both `RPG69_C0A_up.bin` and `RPG69_C1A_up.bin` must be flashed to the device (copy both files to the root directory of an SD card and hold `[SHIFT]` while powering on, as described in [Installing on the Device](../README.md#installing-on-the-device)).

## Status

All 88 active Core 0 patches are implemented in [`manifest/sites.json`](manifest/sites.json) and generated reproducibly by [`tools/gen_manifest.py`](tools/gen_manifest.py), and the Core 1 DSP patch is implemented in [`tools/patch_c1a_dsp.py`](tools/patch_c1a_dsp.py):

- **Track selection toggle & bank switching (`UI-03`, `UI-DIRTY-FDR`, `SEL-03`, `CAVE-01`)**: Pressing the already-selected `SEL1..SEL4` button toggles between Bank A (Tracks 1–4) and Bank B (Tracks 5–8); pressing a different `SEL1..SEL4` button selects that slot within the active bank (`CurTrack & 4`). Updates `0x602D27FC` and `0x61800200` atomically. `UI-DIRTY-FDR` at `0x60035E74` asserts UI dirty bit 4 (`0x10`) so `UpdateFaderRgbLeds` immediately renders the selected bank. Holding `[SHIFT]` (`button 0`) + `[SEL1..4]` enters the `EDIT` menu (`Screen 0x36`) for that track, and pressing `[SHIFT]` + the same track button again while in `EDIT` mode toggles between the `EDIT` menu for the printed track (`1..4`) and the `+4` track (`5..8`).
- **Volume faders & `MULTI` knobs (`FDR-ITCM-TBB`, `FDR-ITCM-CODE`, `KNOB-ITCM-MULTI`, `KNOB-UI-MULTI1`, `KNOB-UI-MULTI2`)**: Replaces the 4 unrolled fader handlers in ITCM (`0x01024FD2..0x01025050`) with a unified bank-aware fader handler (`0x3F + track * 3`) and bank-switches `C1..C4` in `MULTI` knob mode so faders 1–4 and `C1..C4` control Tracks 5–8 whenever Track 5, 6, 7, or 8 is selected. `KNOB-UI-MULTI1` (`0x60036A16`) and `KNOB-UI-MULTI2` (`0x60036B6A`) hook strictly before the `Single` knob-mode branch targets (`0x60036A1A`, `0x60036B6E`) so `System > Knob Trk = Single` works cleanly across all 8 tracks.
- **`SEL1..SEL4` LEDs (inverted for tracks 5–8), fader RGB LEDs, & drum-pad mute (`LED-SEL-CHECK`, `LED-SEL-BLINK`, `FDR-BANK-LOOPBASE`/`FDR-BANK-TOP`/`FDR-BANK-BOT`/`FDR-LED-ID1`/`FDR-LED-ID2`, `MUTE-*`, `SEL-01`)**: Updates `UpdateSelButtonLeds` (`0x600977AC`) so tracks 1–4 illuminate (or flash in `EDIT` mode) the selected button while tracks 5–8 invert the illumination (the other 3 buttons are illuminated/flashing and the selected button is dark); in `UpdateFaderRgbLeds` (`0x60099200`) the loop counter is remapped so **`r7` is the physical fader 0..3** and the loop head rebuilds **`r4 = r7 + bank`** (bank = bit 2 of the selected-track byte `*[*r5+0x10] == 0x61800200`, read locklessly), which makes the record pointer (`record base + r4*0x100`), the record-state param ids (`0x90 + r4`, all 8 dispatched), the engine track-index queries (`uxth r1, r4`) and the selected/record gate bank-aware, while the 2 fader RGB LED ids are unbanked back to `0x1C + physical` (banked `0x1C + r4` would address pad LEDs `0x20..0x23`). Steady colours are now native (they come from `record[banked] + 0x224`, no colour hook needed), so `LED-FDR-COL1..4` and `tramp_fader_color_idx` are deleted (§3, Attempt 12). **Status: hardware verified — bank B (tracks 5–8) flashes red on the selected fader, colours correct in both banks (natively, without the deleted colour hooks), bank A stock.** Drum-pad mute (`SEL1..4 + Pad`) offsets its track index by the active bank.

Consequence to keep in mind: a project that stores tracks 5–8 at very low volume **is** raised to unity 255 on load, and the remembered bank word (`0x602D27FC`) is reset to `0` (bank A) by the load path. Verified 100% 8-track native in the stock MC-101 `.prj` serializer/deserializer (`0x6003E500..0x600466F0`) and project track/clip importer (`0x6008E4B4..0x6008EDFC`).

## User Guide: Drum Pad Deep Edit, WMT1–4 Sample Tools, & Sample Chop

All features below are accessed on a **Drum Track** in **NOTE** mode by holding **`SHIFT` + tapping a Pad** to open the expanded 13-item Drum Pad Sound Menu:

`PRESET` · `PROJECT` · `WAVE FILE` · **`WMT1 WAVE`–`WMT4 WAVE`** · **`PAD EDIT`** · **`WMT1 SMPL`–`WMT4 SMPL`** · **`SMPL CHOP`**

### 1. Expanded Drum Pad Edit (`SHIFT + PAD → PAD EDIT`)

Stock MC-101 only exposes 3 sections in `PAD EDIT` (`PAD EDIT`, a 3-item `INST EDIT`, and `EQ EDIT`). This patch unlocks **11 sections** matching MC-707 drum instrument depth (use `SHIFT + VALUE` dial to jump quickly between sections):

1. **`PAD EDIT:`** *(stock, 13 params)* — Pad Level, Pan, Coarse/Fine Tune, Mute Group, Reverb/Chorus/Delay Sends, Comp/EQ Sw, Output Assign, etc.
2. **`INST EDIT:`** *(expanded, 10 params)* — Voice Assign, Env Mode, WMT Velo, Inst Lvl, Src Key, FineTune, RndPitch, Rnd Pan, Alt Pan, WaveSync.
3. **`WMT1 EDIT:` – `WMT4 EDIT:`** *(4 sections × 23 params each)* — Full per-layer control for all 4 Wave Multi-Tone layers: Switch, Type (`INT`/`SAMP`), Bank, Wave L, Wave R, Level, Pan, Coarse/Fine Tune, Gain, Velo Lo/Hi, Fade Lo/Hi, FXM Sw/Col/Dpt, Rnd/Alt Pan, Delay Mode/Sync/Note/Time.
4. **`TVF/TVA:`** *(8 params)* — Filter Type, Cutoff, Resonance, Cutoff Velo Curve/Sens, Reso Velo Sens, Level Velo Curve/Sens.
5. **`PITCH ENV:`** *(14 params)* — Depth, Velo Sens/Curve, T1/T4 Velo, Time 1–4, Level 0–4.
6. **`TVF ENV:`** *(14 params)* — Depth, Velo Sens/Curve, T1/T4 Velo, Time 1–4, Level 0–4.
7. **`TVA ENV:`** *(14 params)* — T1/T4 Velo, Time 1–4, Level 1–3, and envelope shape controls.
8. **`EQ EDIT:`** *(stock, 8 params)* — Pad 3-band EQ.

### 2. Per-Layer WAV Loading & Sample Edit (`WMT1–4 WAVE` & `WMT1–4 SMPL`)

- **`WAVE FILE`** *(stock behavior)*: Resets the entire pad (clears `WMT2`–`WMT4`, resets pitch/filter/EQ, renames the pad) and loads the chosen WAV into `WMT1`.
- **`WMT1 WAVE` – `WMT4 WAVE`**: Loads a WAV file **non-destructively** into that specific WMT layer (`WMT1`–`WMT4`), keeping all other layers, preset waves, filter/envelope settings, and pad settings intact — ideal for stacking drum hits (e.g., sub + click + acoustic snare + texture) on a single pad.
- **`WMT1 SMPL` – `WMT4 SMPL`**: Opens the stock Sample Edit screen (Start/End/Loop/Gain/Normalize/etc.) directly targeting the User Sample assigned to `WMT1`, `WMT2`, `WMT3`, or `WMT4`.
- **Safe Sample Delete:** The firmware's unused-sample scanner checks all 4 WMT layers (`WMT1`–`WMT4`), so samples loaded into `WMT2`–`WMT4` are properly protected.

### 3. Sample Chop & Pad Assign (`SHIFT + PAD → SMPL CHOP`)

`SMPL CHOP` lets you inspect any User Sample on a Drum Track pad as a live waveform on the 16×2 LCD, slice it into up to **32 chops** (by equal steps, automatic transient detection, or manual placement), audition every slice cleanly in isolation on the pads, and export slices as real standalone User Samples assigned to your Drum Kit pads (which save and reload with your project).

#### Opening & Reading the Display
1. On a **Drum Track** in **NOTE** mode, hold **`SHIFT` + tap the pad** containing your User Sample, scroll to **`SMPL CHOP`**, and press **`VALUE`**.
2. On open, `SMPL CHOP` automatically finds the first WMT layer (`WMT1`–`WMT4`) holding a User Sample, starts with **4 equal slices (`>STEP:04`)**, and isolates audio:
   - Other pads (`Pads 1–16`) are gated so tapping them only auditions slices instead of triggering existing kit sounds.
   - Other WMT layers/presets on the source pad are temporarily muted on Core 1 DSP and automatically restored on `EXIT`.
3. **16×2 LCD Layout:**
   - **Row 1 (top):** Active mode (`>` prefix) and parameters, or temporary status banners (`SLICE ADDED!`, `DONE! 08 PADS OK`, etc.).
   - **Row 2 (bottom):** 16-column live **waveform** of the current zoom window:
     - **Vertical bars** (6 heights): Audio peak amplitude per column.
     - **Solid flat top cap + vertical line:** Active marker (currently selected slice start, or free cursor in `>ADD`).
     - **Small top tick + stem:** All other slice/transient markers visible in the window.

#### Global Controls (Work in Every Mode)
- **Short-press `VALUE`:** Cycles through the 7 modes:  
  `>STEP` → `>AUTO` → `>M01` (Move) → `>ADD` → `>Z` (Zoom) → `>ASGN` → `>SRC`
- **Turn `VALUE` dial:** Adjusts the active mode's primary parameter or moves the marker/cursor.
- **`SHIFT + VALUE` press:** Executes the active mode's action (Delete slice in `Mxx`, Insert slice in `ADD`, Re-detect in `AUTO`, Commit in `ASGN`).
- **`SHIFT + VALUE` dial:** Secondary control (Quick Zoom in `Mxx`/`ADD`, fine sensitivity `±1` in `AUTO`, target layer `W1`–`W4` in `ASGN`).
- **Tap Pads 1–16** *(in `STEP`/`AUTO`/`Mxx`/`Z`)*: Selects and auditions slices `1–16` live; hold **`SHIFT` + Pad 1–16** for slices `17–32`. Releasing the pad stops playback.
- **`EXIT`:** Restores the source sample's original Start/End and original WMT layer switches, and exits (any slices already committed in `>ASGN` remain permanently assigned).

#### The 7 Modes
1. **`>STEP` (Equal-Step Chop)** — e.g. `>STEP:16  S01/16`
   - Turn `VALUE` dial to divide the sample evenly into **`01`, `04`, `08`, `16`, or `32` slices** across `[orig_start..orig_end]`. Tap Pads 1–16 (`SHIFT+Pad` for 17–32) to preview.
2. **`>AUTO` (Auto Transient Detection)** — e.g. `>AUTO:50  N:12`
   - Scans the sample's 128-bin peak envelope and places slice markers on sharp attacks/transients (up to 32 slices).
   - Turn `VALUE` dial to adjust sensitivity **`05`–`95`** in steps of `5` (`SHIFT + dial` for fine steps of `1`) and immediately re-scan: lower values catch only the loudest peaks (fewer slices); higher values catch softer hits/hi-hats (more slices). `N:xx` shows the detected slice count. `SHIFT + VALUE` re-runs detection.
3. **`>M01`, `>M02`, … (Move & Delete Slice)** — e.g. `>M01 012345 Z1x`
   - Tap Pad 1–16 (`SHIFT+Pad` for `M17`–`M32`) to select and hear a slice; the number (`012345`) shows its exact start frame (or milliseconds `...m` on long samples >22 s).
   - Turn `VALUE` dial to nudge that slice's start point left/right (step scales with zoom: 1/16th of the visible window, safely bounded between adjacent slices).
   - `SHIFT + VALUE` dial quick-zooms `1x`–`32x` centered on the selected slice.
   - `SHIFT + VALUE` press **deletes** the selected slice mark (`SLICE DELETED!`, minimum 1 slice kept).
4. **`>ADD` (Manual Add Slice)** — e.g. `>ADD 012345 N:08`
   - Provides a free-roaming cursor on Row 2 to drop new slice marks by hand.
   - Turn `VALUE` dial to position the cursor (`SHIFT + dial` to quick-zoom `1x`–`32x`).
   - Tap any Pad 1–16 to audition audio from the cursor to the end of the sample so you can locate attacks by ear.
   - `SHIFT + VALUE` press **inserts** a sorted slice mark at the cursor (`SLICE ADDED!`, max 32 slices; rejects duplicates within 64 frames / ~1.4 ms or edges).
5. **`>Z` (One-Handed Zoom)** — e.g. `>Z 4x  S01/16 ST`
   - Dedicated one-handed zoom screen (`VALUE` dial selects **`1x`, `2x`, `4x`, `8x`, `16x`, or `32x`** centered on the selected slice) also showing `Sxx/NN` and Stereo (`ST`) / Mono (`MO`). Tapping pads auditions slices and auto-pans the viewport.
6. **`>ASGN` (Assign Slices to Pads & Clear Pads)** — e.g. `>ASGN ALL>P1  W1`
   - Exports each assigned slice as a real truncated User Sample in external Wave RAM (`<SourceName>_01`, `_02`, …), syncs to Core 1 DSP, and binds it to Drum Kit pads for permanent project save/reload.
   - Turn `VALUE` dial to choose target mode:
     - **`ALL>P1`:** Auto-assigns slices `1–16` → Pads 1–16 (on `W1`, wipes old `WMT2`–`WMT4` and silences leftover unused pads).
     - **`ALL>Pxx`:** Auto-assigns slices starting at the current source pad.
     - **`17+>P1`** *(when >16 slices)*: Auto-assigns slices `17–32` → Pads 1–16.
     - **`CLR P1-16`:** One-click clear of `WMT1`–`WMT4` across all 16 pads.
     - **`Sxx>P01` … `Sxx>P16`:** Manual single-slice assign for the currently selected slice (`S01`–`S32`). **Shortcut:** tap any Pad 1–16 while in `>ASGN` to select that destination pad directly.
   - `SHIFT + VALUE` dial chooses target layer **`W1`–`W4`** (`W1` performs a clean pad init & rename; `W2`–`W4` binds non-destructively for layering).
   - `SHIFT + VALUE` press **commits** the assignment.
7. **`>SRC` (Source Pad / Layer)** — e.g. `>SRC P01 W1 02.4`
   - Displays source pad, source layer (`W1`–`W4`), and total sample length in seconds. Turn `VALUE` dial to switch source layer `W1`–`W4`, or tap any Pad 1–16 (with normal pad sound audible) to switch to chopping another pad's sample.

## User Guide: Button Navigation Mode (VALUE Dial Alternative)

Button Navigation Mode provides an optional, global alternative to rotating and pressing the `VALUE` dial — useful for worn encoders or fast one-handed button navigation across every screen and menu on the MC-101 (System, Track, Clip, Preset/WAV browsers, Pad Edit, Sample Chop, etc.).

- **Enter Button Nav Mode:** Hold the **`>`** (Measure Right) button **alone** for **~600 ms**.
  - Short-tapping `>` (< 600 ms) still advances measures/octaves normally.
  - Multi-button combos (`SHIFT + >`, `SEQ + >`, `SEL1–4 + >`, etc.) pass straight through with zero delay.
- **Visual Indicator:** While active, the **`<`**, **`>`**, **`TEMPO`**, and **`EXIT`** button LEDs all **blink continuously** across every screen.
- **Controls while active:**
  - **`<`** → Rotate **`VALUE` dial left (`-1`)**. Hold `<` for continuous auto-repeat scrolling (~320 ms initial delay, then ~10 steps/sec).
  - **`>`** → Rotate **`VALUE` dial right (`+1`)**. Hold `>` for continuous auto-repeat scrolling.
  - **`TEMPO`** → Press **`VALUE` / `ENTER` (OK / Select)**. Holding **`SHIFT + TEMPO`** also works as **`SHIFT + VALUE`**.
  - **`EXIT`** → Normal **`EXIT`** (back / exit menu).
  - **All other buttons & the physical `VALUE` dial** keep their exact stock functions.
- **Exit Button Nav Mode:** Press **`SHIFT + <`**. Immediately exits Nav Mode, suppresses the `<` event, and restores `<`, `>`, `TEMPO`, and `EXIT` LEDs to their normal states.

## Hardware Testing & Investigation Log

This section records every tested failure mode, false hypothesis, and ineffective fix across all hardware testing rounds to prevent recurring regressions.

> **Methodology change (Attempt 9):** Attempts 1–8 were static guesses verified only by flashing; no hook was ever confirmed to execute at runtime. From Attempt 9, each persistent issue is first probed with a diagnostic build before any fix is written. A probe is only admissible if it changes observable behaviour relative to stock (see Attempt 9/10 in §3: forcing the fader loop to `r4 = 0` reproduced stock exactly and yielded no signal).
>
> **Methodology corollary (from the §2 Attempt 9 regression): the absence of a probe signal does not prove code never runs, and "no observed behaviour change" is not proof that code is dead.** The `PI0` popup counter (§3 Attempt 11) was read on `[SEL]` presses — events on the project-load path had already happened — so it never incremented; the counter increment site itself was the suspect, not `PRJ-POST-LOAD`. The static case for the hook looked airtight (no caller ever returned to the patched epilogue site) and it was **wrong** as a basis for deletion: removing `tramp_prj_load_init` brought the zero-volume start of tracks 5–8 straight back on hardware. Rule: before deleting any patch site, re-check the behaviour it was fixing on hardware; a site whose *fix* is invisible in a probe is exactly the kind that gets deleted and regresses.
>
> **Fader RGB LEDs — colours resolved (Attempt 10, hardware verified) — implementation superseded by Attempt 12:** `LED-FDR-COL1..4` hooked the four `record + 0x224` colour-index reads of `UpdateFaderRgbLeds` (`0x60099234`, `0x6009936A`, `0x600993B4`, `0x60099428`) and read the colour of track `fader + (CurTrack & 4)`; the loop, LED ids (`0x1C..0x1F`) and fader param ids (`0x90..0x93`) stayed stock. Reported on hardware: faders show tracks 1–4 colours when a lower-4 track is selected, tracks 5–8 colours when an upper-4 track is selected, and the pad-hit flicker is gone. The **bank-B flash** left broken by that design was closed by Attempt 12 banking the loop itself; the colour sites are deleted there, and the re-verification requirement (methodology corollary above: deleting a site requires re-testing the behaviour it fixed) was met — colours reproduce correctly in both banks on the Attempt 12 hardware test.
>
> **Probe removal (Attempt 11):** the `PROBE-VOL` diagnostics are removed from the build (`CAVE-02` at `0x602D2B00` freed, `bl probe_sel_popup` / `bl probe_load_mark` deleted). No `fw_popup` / `fw_sprintf` references remain. **The conclusion drawn from the probe at the time — that `tramp_prj_load_init` (site `PRJ-POST-LOAD`, `0x60046424`) never executed and its hook was dead code — is retracted**; it rested on the popup counter reading `PI0`, and the hardware re-test after the deletion (upper-4 tracks back to zero volume at load) shows the routine runs and is required. See §2, Attempts 9–10.
> - USB ch 11–20: per-track stems are produced/routed by **Core 1** (`RPG69_C1A/sdram1.bin`, sound engine), not Core 0. Next step is MC-101 vs MC-707 Core 1 comparison (research only).

### 2. Persistent Issue Log: Upper 4 Tracks Volume

**Hardware Symptom**: On loading an 8-track project, tracks 5–8 produce no sound until a different tone is selected then re-selected, or until volume faders are altered. Moving faders either muted them or track volumes start out at zero rather than tracking the physical fader or defaulting to unity (100).

- **Attempt 1: Cache Auto-Init in `get_cur_track` & `itcm_fader_entry`**
  - *Hypothesis*: Checking `tone_level_cache[4] == 0` at `0x200199F8` and setting it to 100 would unmute tracks 5–8.
  - *Result*: Ineffective. Upper tracks remained silent until tone re-selection.
  - *Root Cause*: `tone_level_cache` in DTCM is only a multiplier used during synth voice note rendering; the mixer channel volume in the DSP sound engine is separate and controlled via IPC queue messages.
- **Attempt 2: Cache Init in `tramp_prj_load_init`**
  - *Hypothesis*: Initializing `tone_level_cache[0..7] = 100` (`0x200199F8`) on project load would ensure all tracks are unmuted.
  - *Result*: Ineffective. Did not update the DSP mixer's internal track volume state.
- **Attempt 3: UI Shadow Parameter Setting via `fw_set_param`**
  - *Hypothesis*: In `tramp_prj_load_init`, reading physical faders `0x3F + track*3` and writing upper faders `0x4B + track*3` (and levels `0x0F + track = 100`) via `fw_set_param` would configure the volume.
  - *Result*: Partially effective on the UI side (adjusting faders worked afterwards instead of muting to silence), but track volumes started out at ZERO on load until moved.
  - *Root Cause*: `fw_set_param` (`0x6009CB9C`) only writes the UI shadow parameter struct in RAM. It does **not** send an IPC message to notify the real-time DSP sound engine mixer queue (`0x60394A08`).
- **Attempt 4: Calling `fw_update_track_vol` (`0x6032DB4E`)**
  - *Hypothesis*: Calling `fw_update_track_vol` for all 8 tracks (`0..7`) would push the volume to the hardware mixer.
  - *Result*: Ineffective. Track volume remained at zero on initial load.
  - *Root Cause*: Reverse-engineering of `0x6032DB4E` revealed it is a **getter** (`return *(uint *)(r0 * 0x14 + 0x200199f8)`), not a setter or updater. Calling it did nothing.
- **Attempt 5: Dispatching DSP Messages via `fw_set_dsp_param` (`0x6006C82C`)**
  - *Hypothesis*: Calling the true Area 2 parameter setter `fw_set_dsp_param` (`0x6006C82C`) directly sends IPC messages to queue `0x60394A08` for fader parameters `0x4B..0x54` and level parameters `0x0F..0x12`.
  - *Result / Status*: Blocked from hardware test because Boot Failure 7 (`0x40026468/46c` write in crossbar init) tripped prior to project loading.
- **Attempt 6: Setting Level Parameters `0x0F..0x12` Overwrote Active Clip Index**
  - *Hypothesis*: Writing 100 to Area 2 parameter `0x0F + track` sets clip level.
  - *Result*: Upper tracks initialized with zero volume; adjusting fader made sound immediately.
  - *Root Cause*: Area 2 parameters `0x0B..0x12` are **active clip indices** (0..15), not levels! Writing 100 corrupted the active clip index to non-existent clip 100. When voices rendered, `0x6032DB4E` failed clip lookup and muted the track to 0.
- **Attempt 7: Preserve Clip Index, Default Unity 255 / Fader Sync via DSP Queue**
  - *Implementation*: Removed all writes to Area 2 parameters `0x0F..0x12`. Reads physical fader `0x3F + track*3`, defaults to 255 (unity BMC gain) if `<= 0`, sets Area 2 fader parameter `0x4B + track*3` in UI table via `fw_set_param`, and dispatches directly to Sound Engine DSP queue via `fw_set_dsp_param` (`0x6006C82C`).
- **Attempt 8: Universal Post-Load Exit Hook (`PRJ-POST-LOAD` at `0x60046424`)**
  - *Hypothesis / Analysis*: In Attempt 7, `PRJ-LOAD-INIT` at `0x6005B452` was located inside the Screen 0x17 project load dialog event handler. It was **never executed** during a cold boot into a project or during direct project load (`FUN_600513a4` / `FUN_60054ae4`). As a result, on cold boot, upper-4 tracks initialized with volume 0 in the DSP sound engine.
  - *Implementation*: Moved initialization hook from `0x6005B452` to the universal project load completion exit at `0x60046424` (`PRJ-POST-LOAD`, 6 bytes: `b.w tramp_prj_load_init; nop`). `FUN_600462C8` is the common function called by all project-loading paths (`FUN_600513a4` cold boot, `FUN_6005b3f0` dialog, and `FUN_60054ae4` reload). `tramp_prj_load_init` initializes `tone_level_cache[0..7] = 100`, sets Area 2 parameters `0x4B..0x54` to 255 via `fw_set_param(2, 0x4B + r4*3, 255)`, and directly dispatches value 255 to the Sound Engine DSP mixer queue via `fw_set_dsp_param(255, 0x4B + r4*3)` for tracks 5–8 before restoring stack and returning to caller.

- **Attempt 9: "Dead Code" Removal — `PRJ-POST-LOAD` + `tramp_prj_load_init` deleted (47 → 46 sites)** — *retracted by Attempt 10*
  - *Basis at the time (both arguments shown invalid by Attempt 10)*: (1) the probe build of §3 Attempt 11 showed the popup counter reading `PI0` on every `[SEL]` press, read as "`tramp_prj_load_init` never executes"; (2) the static reading of the enclosing project-load function suggested its epilogue slot `0x60046424` was never returned to. The follow-up behaviour test ("tracks 5–8 audible at load, no fader touch") was run on the probe-cleanup build, which **still contained the hook** — it was never a test of the hook's absence, so it proved nothing about it.
  - *Implementation*: Deleted the `PRJ-POST-LOAD` site (`0x60046424` restored to stock) and the `tramp_prj_load_init` cave routine, together with the externals it alone used (`fw_set_param` `0x6009CB9C`, `fw_set_dsp_param` `0x6006C82C`, `fw_load_exit` `0x600462C8`). `CAVE-01` usage dropped to 254 of its 512 bytes. The verifier was changed to assert **stock** bytes at `0x60046424` (and over `0x6005B452..0x6005BEA0`) so the "dead" hook could not silently return — which is why this regression could pass CI.
  - *Root Cause of the mistake*: the probe had **no positive control** — the counter is incremented only by a `bl probe_load_mark` inside `tramp_prj_load_init` itself, so `PI0` is equally consistent with "the increment/display path is broken" and "the code never runs"; it was never demonstrated that the probe's own counting path worked. An unconfirmed negative, reinforced by a static reachability argument, was promoted to proof.
  - *Hardware Result*: **Regression.** With the hook gone the original symptom returned — tracks 5–8 start at **zero volume** on project load (silent until a fader is moved / tone re-selected). `PRJ-LOAD-PRESERVE` alone is *not* sufficient for the upper bank's DSP mixer state; the unity-255 dispatch through `fw_set_dsp_param` is exactly what unmutes tracks 5–8 at load (the mechanism identified in Attempt 5).
  - *Rule established*: never delete a patch site on the strength of a probe reading alone. Deleting a site requires re-testing, on hardware, the behaviour that site was fixing.

- **Attempt 10: Restore `PRJ-POST-LOAD` + `tramp_prj_load_init` (46 → 47 sites)**
  - *Implementation*: Re-inserted `tramp_prj_load_init` in `CAVE-01` and the `PRJ-POST-LOAD` hook (`0x60046424`: `b.w tramp_prj_load_init; nop`), with the externals `fw_set_param` (`0x6009CB9C`) and `fw_set_dsp_param` (`0x6006C82C`). The routine is byte-identical to the hardware-verified Attempt 8 build apart from the deleted `bl probe_load_mark`, and lands at the same address `0x602D26FE`. `CAVE-01` is back to 346 of 512 bytes. `fw_load_exit` (`0x600462C8`) stays deleted (unused), `PRJ-LOAD-INIT` (`0x6005B452`) stays stock, the probe code and `CAVE-02` stay freed.
  - **Frame contract (load-bearing, documented in the source and enforced by the verifier)**: `PRJ-POST-LOAD` replaces the *epilogue* of the enclosing project-load function, stock bytes `0ab0bde8f087` = `add sp, sp, #0x28` + `pop.w {r4-r10, pc}`. `tramp_prj_load_init` therefore **tail-calls** that epilogue: it opens with `sub sp, sp, #8` and ends with `add sp, sp, #0x30` + `pop.w {r4-r10, pc}` (`0cb0bde8f087`) — `−0x08 + 0x30 == +0x28` with an identical register mask. No pushes may be added and neither `sp` constant may change.
  - *Verification (static)*: `tools/verify_patched_image.py` checks the contract from both sides — stock epilogue bytes at the site, the manifest's patch bytes, a hand-decoded `b.w` target (no Capstone dependency, so CTest enforces it even without Capstone installed), the `sub sp, sp, #8` entry bytes, and the `add sp, sp, #0x30; pop.w {r4-r10, pc}` tail inside the routine the branch lands in.
  - *Status*: image and container rebuilt, both CTest suites pass; **awaiting the next hardware flash** to confirm the upper-4 volume is back to the Attempt 8 behaviour.

### 3. Persistent Issue Log: Fader LED Illumination & Pad Hit Flicker

**Hardware Symptom**: The physical fader RGB LEDs mostly illuminate with the colors assigned to upper tracks 5–8, even when a lower track is active. When a lower track (1–4) is selected, hitting a pad causes the fader LEDs to briefly flicker to the lower track colors before snapping back to the upper track colors.

- **Attempt 1: Calling `fw_get_param(3, 0, -1, 0)` in `UpdateFaderRgbLeds` (`0x60099200`)**
  - *Hypothesis*: Reading parameter `3` (active track) on each LED refresh cycle would dynamically select the correct bank.
  - *Result*: Fader LEDs were permanently locked to upper bank colors (tracks 5–8).
  - *Root Cause*: `UpdateFaderRgbLeds` executes inside a high-frequency timer interrupt service routine (ISR). `fw_get_param` calls RTOS mutex acquisition (`0x600384f4`), which fails in interrupt context and returns error code `-1` (`0xFFFFFFFF`). Masking `-1 & 4` yields `4`, forcing the routine to treat bank 2 as permanently active.
- **Attempt 2: Storing Active Track in `0x60A8F6D4`**
  - *Hypothesis*: Writing the active track to `0x60A8F6D4` on `SEL1..4` presses and reading it without mutex calls in `get_cur_track` and ITCM fader routines would avoid RTOS mutex failures.
  - *Result*: Fader LEDs still mostly showed upper track colors and briefly flickered on pad hits.
  - *Root Cause*: Memory address `0x60A8F6D4` is located at offset `+0x268` inside `UI_STATE` (`0x60A8F46C`). Main-thread UI event loops and pad hit ISRs continuously write internal UI flags to this address with bit 2 set (`val & 4 != 0`). Every pad hit overwrote the active track variable, forcing bank 2.
- **Attempt 3: Dedicated Atomic Variable `cur_track_var` at `0x602D27FC`**
  - *Hypothesis*: Placing the atomic active track variable in dedicated SDRAM (`CAVE-01` tail word `0x602D27FC`) prevents UI struct collisions and allows lockless atomic reads from both SDRAM and ITCM.
  - *Result / Status*: Blocked from hardware test because Boot Failure 7 tripped beforehand.
- **Attempt 4: Unsynchronized `0x61800200` & Missing UI Dirty Flag `0x10`**
  - *Hypothesis / Analysis*: In Attempt 6, `cur_track_var` at `0x602D27FC` was tested on hardware. Fader LEDs still mostly showed Bank B and flickered on pad hit.
  - *Root Cause*:
    1. `UpdateFaderRgbLeds` (`0x60099200`) compares track `r4` with active track `*0x61800200` (`ldrsb.w r3, [r2]`). `resolve_sel_track` was only writing to `0x602D27FC` and never updating `0x61800200`, leaving stale unbanked data in the stock struct.
    2. Stock `HandleButtonPress` at `0x60035E74` executes `orr r1, r1, #0x41` (dirty bit 0 and 6). It **never sets bit 4 (`0x10`)** for `UpdateFaderRgbLeds`! Only pad hits set bit 4 (`*0x605C4E10 |= 0x10`), explaining why fader LEDs only refreshed when a pad was hit.
  - *Implementation (Attempt 7)*:
    1. `resolve_sel_track` writes `r6` to BOTH `0x602D27FC` AND `*(int8_t*)0x61800200`.
    2. `tramp_prj_load_init` initializes both variables to 0.
    3. Patch `UI-DIRTY-FDR` at `0x60035E74`: replaces `41f04101` (`orr r1, r1, #0x41`) with `41f05101` (`orr.w r1, r1, #0x51`), asserting dirty bit 4 on every `SEL1..4` button press for instantaneous fader LED updates.
- **Attempt 8: Decouple Background Screen Evaluation from Bank Mutation (`SEL-03`)**
  - *Root Cause Identified*: `UpdateFaderRgbLeds` (`0x60099200`) was functioning correctly, but patch `SEL-03` at `0x60065E04` in `HandleEmptyTrackScreen` (`FUN_60065a84`) was calling `resolve_sel_track`. Because the UI periodically evaluates screen handlers in the background, `resolve_sel_track` was repeatedly called without a button press and re-latched `4` into `0x602D27FC`. When a pad was hit, `UpdateFaderRgbLeds` briefly displayed the lower-4 colors before the background screen task snapped `0x602D27FC` back to `4`.
  - *Implementation*: Replaced `SEL-03` target with `tramp_sel_empty`. `tramp_sel_empty` computes candidate track `(r4 - 6) + (get_cur_track() & 4)` and calls `fw_is_trk_alloc` (`0x60052158`) directly, without ever calling `resolve_sel_track` or writing to `0x602D27FC`. Bank state is now mutated solely on physical button press events.
- **Attempt 9: `PROBE-LED` Forced-Loop Probe (void probe)**
  - *Hypothesis*: Force the `UpdateFaderRgbLeds` loop index to one bank and observe the physical fader LEDs; steady colours would prove that `0x60099200` is the writer of LED IDs `0x1C..0x1F` and that the bank variable was the only fault.
  - *Result*: Probe produced **no diagnostic signal**, so the reported "no visible change" is inconclusive.
  - *Root Cause (probe defect)*: Stock `movs r4, #0` runs at `0x60099204`, **before** the hook site `0x6009920A`. Forcing `r4 = 0` in `tramp_fader_led_init` therefore reproduced stock behaviour bit-for-bit. Any future loop probe must force the *opposite* bank (or an off-palette colour) to be observable.
  - *Static findings that survived*: In normal operation `UpdateFaderRgbLeds` (`0x60099200`, UI dirty bit 4 of `0x605C4E10`) is the only Core 0 writer of LED IDs `0x1C..0x1F` (besides the LED test screens `0x6005A91E..0x6005AA7E` and the colour-preview callback `0x60064DA8`). All four LED setters (`FUN_6001E6B8` set, `FUN_6001E604` resend-all, `FUN_6001E628` set-all, `FUN_6001E680` colour-only) share a **single** shadow pair (modes `0x605C3FA8`, colours `0x605C3FD8`), so a periodic "resend all 48 LEDs" pass cannot stale-snap the fader colours — the periodic-resend desync hypothesis is dead.
- **Attempt 10: `r4` Loop Remap Was Itself the Bug (colour-index hooks replace it)**
  - *Root Cause identified (static)*: The loop base literal `0x602CDCC8 = 0x61991810` is a **`-0x200` biased base**. The loop reads fields at `record + 0x204 / 0x218 / 0x224 / 0x23c` with stride `0x100`, i.e. the real 256-byte track records start at **`0x61991A10`** and `r4` indexes **tracks 1..4 (bank A)** with fields `+0x04` (mode), `+0x18`/`+0x3c` (mute flags), `+0x24` (**track colour index**). Palette at `0x602CDCD0`: indices `0..11` = fixed colours (red, orange, yellow, green, blue, purple, magenta, white, cyan, …), indices `12..19` = the 8 track colours (`d5271c, ff7d27, ffee00, 94e02f, 20e020, 00e0ea, 006cd2, 9c4eac`), bounds-checked by `cmp r0, #0x14`.
    Remapping the loop index to `CurTrack & 4` (`LED-FDR-INIT` / `LED-FDR-LOOP` / `LED-FDR-ID*`) made the loop read records 4..7, i.e. the colour indices of **tracks 5..8** — the patch itself produced the reported symptom "faders show bank B colours while bank A is active". The same remap also moved the fader param ids from `0x90..0x93` to `0x94..0x97` and shifted the blink/mode branches onto the wrong records.
    *(The parenthetical judgement attached to that sentence at the time — "0x94..0x97 **not defined**" — was wrong and is corrected here: all 8 param ids `0x90..0x97` are dispatched. The state getter `0x600331E0` has unrolled read arms for `UI_STATE+0x438..0x454` at `0x60033960..0x60033998`, the setter `0x60033AFC` has matching store arms at `0x60034198..0x600341C2`, and the record-state writer `0x6006595C` (bound `cmp r4,#8` at `0x600659FA`) and clearer `0x60065F00` (bound 8 at `0x60065F10`) write all 8 slots. `0x94..0x97` are defined and maintained for tracks 5..8; the failure was on the **consumer** side, in the 4-capped loops (see Attempt 12).)*
  - *Implementation*: Restored the stock loop, LED ids and param ids (`r4 = 0..3` = physical faders `1..4`) and hooked **only the colour-index reads**: `LED-FDR-COL1..4` replace `ldrsb.w r0, [r0, #0x224]` at `0x60099234` (steady path), `0x6009936A`, `0x600993B4`, `0x60099428` (selected-track/flash paths) with `bl tramp_fader_color_idx` (`0x602D2694`), which reads the colour index of record `r4 + (CurTrack & 4)` — the track the fader really drives. Colours now follow per-track colour assignments of the active bank; dirty-bit refresh (`UI-DIRTY-FDR`) repaints on `[SEL1..4]` presses.
  - *Known side effect*: the stock blink/flash branch (`0x600992C6`) is gated by `byte[*0x61800200] == r4 && byte[*0x61800200 + 5] == 1` (`*0x61800200` is a **byte** holding the selected track index, not a pointer). With the loop left bank A-relative, that gate cannot match in bank B, so the selected fader no longer flashes/flips to red (`0xff0000` at `0x600992DE` / `0x6009931C`) for tracks 5..8. Restoring flash fidelity in bank B needs a hook at the gate (`0x6009922C`, `cmp r3, r4` → compare `r4 + bank`) plus bank offsets on the `uxth r1, r4` state queries at `0x600992D2`, `0x600992F6`, `0x60099302`, `0x6009930C`.
  - *Hardware Result (verified, issue closed)*: Faders 1–4 illuminate with the colours of tracks 1–4 while a lower-4 track is selected, and with the colours of tracks 5–8 while an upper-4 track is selected; the pad-hit colour flicker is gone in both banks.
- **Attempt 11: Probe Cleanup (48 → 47 sites)**
  - *Implementation*: Removed the `PROBE-VOL` diagnostics — deleted the `CAVE-02` site (`0x602D2B00..0x602D2BFF` is free zero padding again) and dropped `bl probe_sel_popup` (`tramp_sel_main`) and `bl probe_load_mark` (`tramp_prj_load_init`). No `fw_popup` / `fw_sprintf` references remain in `CAVE-01`.
  - *Carried-over observation — **retracted***: in the probe build the popup counter never incremented (`PI0` on every `SEL` press, while the `T`/`F`/`L` fields rendered), which was read as "`tramp_prj_load_init` reached via `PRJ-POST-LOAD` (`0x60046424`) does not execute". That reading is **invalid**: the counter has no positive control (it is incremented by code inside the very routine whose liveness was being tested), and the follow-up behaviour test ("tracks 5–8 play without touching the faders") was run on this probe-cleanup build, which still contained the hook. The hardware test of the *next* build, after the hook was deleted, showed tracks 5–8 starting at zero volume — the hook runs and is required. See §2, Attempts 9 and 10.
- **Attempt 12: Bank the `UpdateFaderRgbLeds` loop itself (47 → 48 sites; bank-B record/flash fidelity)**
  - *Goal*: close Attempt 10's known side effect — the selected fader must flash/flip to red for tracks 5..8, and the steady/record state of a fader must come from the record of the track it really drives, without per-field hooks.
